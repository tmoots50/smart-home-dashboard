## Active limitations
*(known gaps we're living with for now — explicit accept-it-for-now decisions)*

- **Pi's LAN IP is not reservation-locked.** Currently `10.0.0.110` via DHCP lease; could rotate after a router reboot or lease expiry. Decided 2026-05-01 to skip the Xfinity DHCP reservation flow because Tailscale already provides a permanent stable address (`dashboard` / `100.123.125.112`) that works inside and outside the LAN. Revisit if: (a) we add another LAN device that needs to hit the Pi by hardcoded IP, (b) Tailscale ever has an outage that costs us real time, or (c) DHCP rotation actually shifts the IP and breaks something. Xfinity reservation requires enabling Admin Tool access in the Xfinity app first, then `http://10.0.0.1` → Connected Devices → Edit → Reserved IP.

- **Light/dark toggle — user-reported regression that I could NOT reproduce (2026-07-26; parked for a later session).** Tim reported the toggle regressed after the morning's calendar week-grid work and will supply the exact symptom + device next session. **Evidence gathered:** the toggle's code (`theme-mode.js` + the `data-launch="theme"` handler in `morning-briefing.js`) is UNCHANGED by every 2026-07-26 commit — the calendar commits (`bd0b25e`/`dec1aa2`/`c41627d`) touched only `calendar.js` and `.calweek__*` CSS (scoped, no bleed onto `.action-btn`, no `!important`/`:root`/`html` rules); the 29 theme(-mode) tests pass. Driving the **live** dashboard in clean Chromium (Playwright): the toggle flips `cosy↔fun`, body background dark↔light, `color-scheme` dark↔light, and the sun/moon icon swaps — reversible, with zero JS/console errors, **including** with the Morning Brief forced visible (the only morning-specific state) and across a full on→off→on cycle. So the morning calendar update did **not** break the toggle in a standard browser. **Leading hypotheses (unverified — need Tim's symptom):** (a) wall-tablet-specific: Fully Kiosk serving a **stale cached bundle** — try a hard refresh on the tablet first; (b) Android **system dark mode re-enabled** → WebView force-dark (the 2026-07-19 `color-scheme` fix should prevent this, but verify the OS setting); (c) a new pinned URL param or a transient localStorage `theme:override`. Both historical failure modes (the `?theme=` precedence bug + WebView force-dark, see the 2026-07-19 resolved entry) are already fixed and verified, so this is a new mechanism or an environmental regression on the tablet, not a code regression from the calendar work. To reproduce next time: Playwright against the live URL, click `[data-launch="theme"]`, assert `document.documentElement.dataset.theme` flips and watch `pageerror`.

- **Touch calibration off after screen rotation (transform=270)** — *Resolved 2026-05-01.* Root cause was double-rotation: the udev rule applied `LIBINPUT_CALIBRATION_MATRIX` at the libinput layer, AND labwc's `rc.xml` applied the output transform via `<touch mapToOutput="HDMI-A-1"/>`. Both layers rotating compounded into the "close but off" symptom. Fix: removed `/etc/udev/rules.d/90-cocopar-touch.rules` (renamed to `.disabled-2026-05-01`), let labwc + `mapToOutput` own touch rotation alone. Verified taps register accurately after reboot. Lesson: on modern wlroots compositors, prefer compositor-level touch mapping over libinput calibration — the two don't compose.
